## 成果物
### 企画
- 想定読者: DB のテーブル設計にあまり詳しくない。アンチパターンがあることは知っている。自分なりの手順やこだわりはない。AI が出した設計をよく理解しないまま「じゃあそれで」と採っている
- スタートポイント: テーブル設計は AI と相談して作る（人が作った DB 設計のエージェントスキルを入れていることもある）
- 懸念される出来事: 空（読者はまだきっかけに出会っていない）
- R1: UPDATE で上書きする表になっていて、過去の値が消え、取り戻せない。しかもそれに気づいていない（わかったうえで上書きしているなら問題ない）
- R2: ユースケースの洗い出しから出発して、RDB の表ができあがるまでを、一通り思い描けるようになる
- 読者がすでに試したこと: AI と相談しながら設計している。DB 設計のスキルを入れていることもある
- 軸（開発者が案1を選んだ）: /erd-design の 5 フェーズ（抽出・正規化・表現方法・関係・検証）を軸にする。通しの例は #523（目標を立てる）。山場はフェーズ3「変わる値を決める」（構造フェーズで #977 を外し、導入は例え話に替えた。下の「構造」）

### 素材（確かめた事実。出どころつき）
- nu-tori: 公開リポジトリ gn-t-k/nu-tori。clone は /home/user/nu-tori（セッションに追加済み。Issue は mcp__github__issue_read で読める）
- /erd-design: 開発者の自作（mattpocock/skills の写しではない。skills-lock.json にも無い）。置き場は .agents/skills/erd-design/（.claude/skills/ はシンボリックリンク）。SKILL.md と references/{general-rules, output-template, phase1〜5, table-design-rules}.md
  - 参考に挙げている外部資料: イミュータブルデータモデル（kawasima さんの Scrapbox）、1:N でも中間の表を検討する（zenn.dev/praha/articles/65afb28caacd0b）、ミックさんの NULL の記事（mickindex.sakura.ne.jp/database/db_getout_null.html）
  - 構成: メインのエージェントはフェーズの進行とユーザーとの対話を受け持ち、作業はフェーズごとに新しいサブエージェントに任せる（先のフェーズの手順が見えると今のフェーズを急ぐため）。出力ファイルが正本。確かめるときは選択肢と pros/cons で尋ねる。先のフェーズの話はパーキングロットへ
  - phase1: イベント系（「〜する」「〜日」）から先に抽出し、リソース系はイベントの誰が・何を・どこでから見つける。「あるときだけ値が入る属性」（キャンセル日時など）はイベントにする
  - phase3: 「UPDATE と DELETE で値を書き換える設計は、既定では避ける」。採るのは「クエリが書けないほど複雑」「速さが致命的に落ちる」「プロジェクトの決まりがそう定める」のときだけ。変わる値は 5 つの条件（過去の値を見る画面・監査・時機や理由の確認・ほかの状態に効く・将来履歴が要りそう）でイベントの表に分けるかを判断。どれにも当たらず書き換えるなら、将来要る場面と互換を示してユーザーに委ねる
  - table-design-rules: enum・CHECK を使わずアプリで確かめる／分けるかは事実の数で決める（JOIN の複雑さは理由にしない）／センチネル値を使わない。NULL を許す日時の列はイベントの表へ（NULL を避けるためでなく UPDATE を避けるため）／時刻の列は事実で名付け、created_at・updated_at を一律に付けない
- nu-tori の進め方: docs/agents/table-design.md（仕様ごとに差分で /erd-design を回し、決まった ERD を仕様の Issue の Schema changes に書く。記録の DB はアカウントごとに1つなので、表はアカウントを指す列を持たない）
- #977（体重記録の直し。実装済み・PR #1080 でマージ、Issue は closed）:
  - 経緯: 体重記録は「同期の仕組みを端から端まで通す最初の一本」として作り、/erd-design の進め方を足した日と同じだったが、工程に乗らなかった。直すと UPDATE で上書きしていた
  - 問題の節: 「体重が勝手に変わった」という問い合わせに、どの端末がいつ何を送ったかを DB から説明できない（観測の道具には体重の値を送らない決まり ADR-0017 なので、値の履歴を見られるのは DB だけ）／直す前の値を見せる・戻す機能をあとから足せない／体重記録だけ形が違い、新しい種類を足すときに真似される元になる
  - 解決: 体重記録の行は作ったときの値のまま。直したら体重の修正・時刻の修正を書き足す。今の値は受け取った順でいちばんあとの修正。版は列に持たず「1＋直す控えの数」で出す
  - 移行 0014: 直す前の値は上書きで失われていて戻せないので、移行の時点の今の値を埋め戻す（server/durable-object-migrations/0014_create_weight_record_corrections.sql、server/src/weight-record/durable-object/weight-record-tables.ts のコメント）
  - 範囲の外: 直す前の値を画面に出すこと・戻す機能（今は見せる場面が無い）。記事で「今、履歴を見せている」とは書かない
  - 「28 の判断」
- #332（食事を直す）: 「/erd-design のフェーズ3の既定に従い、出来事として足す」。cons として「今の値を読むたびに出来事を引いて並べる」を明記。UPDATE は無い。DELETE は料理・食事を消すときの中身だけ。理由は「プライバシーポリシーの『消したものの ID を、消したことの印として残します』『どの食事の分だったかは残りません』に合わせる」。その代わり「消した料理を『元に戻す』は、サーバーではできない」
- #523（目標を立てる）: 表は 8 つ、どれも書き足すだけ。NULL を許す列なし。維持の目標・閉じていない目標は、サブセットの表・イベントの表に行が無いことで表す（weight_change_goals、goal_closures）。今の目標は「閉じた行の無い目標」。設計判断 53 個（大半は理由が書かれていない）。理由がある例: 「あとで目標を立て直しても、その日の評価が変わらないため」

- #647（課金）: 「『今の状態』を1行に持って通知で書き換えない。順番が入れ替わった通知も、届いた取引を全部持てば同じ答えになる」。例外として test_users は外すとき行を消す（D26）。判断の番号は D1〜D65（65 個とは書かれていない）
- #647 の順番の入れ替わりの根拠（確かめた）: Apple「Responding to App Store Server Notifications」に「順不同で届く」とはっきり書いた文は無い。送り直しの決まりはある: 成功を返さなかった V2 の通知は「at 1, 12, 24, 48, and 72 hours after the previous attempt」に送り直す（本番だけ。Sandbox は1回）。signedDate は送り直しでも変わらない。ここから、受け損ねた古い通知が新しい通知より遅れて届きうる。#647 のテストの決定にも具体例（請求の失敗が、請求を取り戻した更新より遅れる、同じ取引の古い写し、戻しが取り消しより先）。頻度は、サーバーが受け損ねたときだけでまれ。記事では「まれだが、起きたら上書きの表は古い状態に戻る」と書く。nu-tori の docs/research/app-store-subscription.md にも同じ引用
- #523 の補足: 表8つは goals、weight_change_goals、goal_closures、goal_decision_receipts、expenditure_estimates、initial_expenditure_estimates、daily_guides、daily_guide_limit_hits。設計判断は1〜53の番号つきで Issue 本文の Schema changes にある

### 構造（ステップ 8 まで済み。構造フェーズ完了。次は狙いワードの仮決め→導入）
- 主題: ユースケースから RDB の表を設計する工程（上書きしない表の作り方）
- S: 表は AI と相談して作り、提案をそのまま採っている
- C: 提案された表が UPDATE で上書きする形だと、過去の値が消えて取り戻せない。表の定義を見ても気づきにくい。例え話: 目標を立て直すたびに1日の目安を上書きする表だったら、あとで「過去の日をその日の目安と比べて振り返る」機能を作ろうとしたとき、昔の目安が残っていない
- Q: ユースケースから表まで、どう進めれば「値を残すか消すか」を自分で決めた表になるのか
- A（主ポイント）: 工程を5つに分けて進める。出来事を先に洗い出し、変わる値は書き足すのを既定にし、上書きと削除は理由があるときだけ選ぶ。最後に疑似 SQL で今の値を引けることを確かめる
- キーライン:
  0. 前置き: 工程の全体像と AI との回し方（フェーズごとのサブエージェント、出力ファイルが正本、pros/cons で尋ねる、パーキングロット）。短く、スキルへのリンク
  1. 出来事を先に洗い出し、物はそこから見つける（#523 判断6: 決める・閉じる・達成・期限の日の確定を別の出来事に。閉じた日を goals の NULL 可の列にせず goal_closures）
  2. 一つの事実は一か所に置く。分けるかは事実の数で決める（判断15: 受け取りは時刻を持たない＝decided_at と同じ事実。判断16: 閉じた日は次の目標の started_on から出す）
  3. 【山場】変わる値は書き足すのを既定にし、上書きと削除は理由で選ぶ。3a〜3c は全部入れる（選択肢ではない）
     - 3a: 種類はサブセットの表（weight_change_goals。判断28）、値が無いことは行が無いことで表す（NULL 可の列ゼロ。判断32）。今の目標は引き方で出す（判断33）
     - 3b: 書き足す理由（1）あとで使いたくなる過去の値: #523 ストーリー68「過去の日を見る人として、その日に当たっていた1日の目安と比べたい。あとで目標を立て直しても、その日の評価が変わらないため」。#613 の同じ型の理由はひと言だけ（2）順番が入れ替わる事実: #647 判断1「『今の状態』を1行に持って通知で書き換えない。順番が入れ替わった通知も、届いた取引を全部持てば同じ答えになる」、ストーリー58
     - 3c: 消す理由: プライバシーポリシーの約束（#332）。代わりに「元に戻す」はサーバーでできない
  4. 関係: 子に外部キーを直に置くか中間の表を足すか（判断39: 直に置く。判断38: goal_closures が goals を2回指す）
  5. 疑似 SQL で今の値を引けるか確かめる（読む口: 今の目標＝goal_closures に行の無い目標）。書き足す形の代償（#332「今の値を読むたびに出来事を引いて並べる」）を確かめる段
  - 結び: R2 を振り返り、nu-tori を紹介
- 決めた書き方:
  - #523 の判断がどのフェーズで決まったかは記録が無い（Issue に判断53個が並ぶだけ）。開発者の判断で、Mac で .scratch を探さず、「#523 の判断を工程の順に並べ直すと」と書く。実際の記録をなぞったようには見せない
  - #977 は取り上げない（開発者: テーブル設計のミスでなくプロセスのミス＝tracer bullet に erd-design を当てなかった）。導入の対比も使わない
  - 「体重が勝手に変わった」問い合わせは来たことがない（開発者）。問い合わせの話は書かない
  - 判断6・16・39 は Issue に理由が無い。開発者の選択（案A）で、「スキルの決まりに当てはめると、こうなる」と効果として書き、当時の意図としては書かない（サポートの［分析］）

### サポート
出どころ: [523-判断N] は #523 Schema changes の設計判断、[skill-pN] は /erd-design の references/phaseN、[332] [613] [647] は各 Issue。［分析］は Claude が表から確かめたこと（意図としては書かない。開発者が案Aで決めた）
- 0 前置き
  - 5フェーズを1行ずつ: 抽出（イベントから）／正規化（1つの事実を1つの場所に）／表現方法（サブセット・無い値・変わる値）／関係（多重度・外部キー・中間の表）／検証（擬似 SQL）[skill]
  - AI との回し方: フェーズごとに新しいサブエージェント（先の手順が見えると今のフェーズを急ぐため）、出力ファイルが正本、確かめるときは選択肢と pros/cons、先のフェーズの話はパーキングロット [skill SKILL.md]
  - nu-tori での使い方: 仕様ごとに差分で回し、決まった ERD を仕様の Issue の Schema changes に書く [docs/agents/table-design.md]
  - 通しの例 #523 の結果: 表8つ、どれも書き足すだけ（UPDATE も DELETE も無い）、NULL を許す列なし [523 Schema changes]。この結果に至る判断を工程の順に並べ直す、と断る
- 1 出来事を先に
  - 決まり: 「〜する」「〜日」のイベントから先に抽出し、物はイベントの誰が・何をから見つける。あるときだけ値が入る属性（キャンセル日時など）はイベントにする [skill-p1]
  - #523 で: 目標を閉じる・達成・期限の日の確定を、目標とは別のイベントにした [523-判断6]。閉じることは goal_closures の行になり、閉じていない目標は行が無いことで表す [523 NULL の節]
  - 対比［分析］: goals に closed_on（NULL を許す）を持つ形だと、閉じるたびに目標の行を UPDATE する。決まりは「NULL を避けるためでなく UPDATE を避けるため」[table-design-rules]
- 2 1つの事実は1か所
  - 決まり: 1つの事実を1つの場所にだけ置く。導出項目は元から常に出し直せるか（可逆性）で持つか外すかを決める [skill-p2]。分けるかは事実の数で決め、JOIN の複雑さは理由にしない [table-design-rules]
  - 判断15: 要求の受け取りは受け取った時刻を持たない（目標の decided_at と同じ事実）
  - 判断16: goal_closures は閉じた目標と次の目標だけを持ち、終わった日・閉じた時刻は次の目標の started_on・decided_at から出す
  - ［分析］判断16 の形なら、終わった日と次の目標の開始の日が食い違うことが起きない（同じ日を2か所に持たない）
- 3 山場
  - 3 の決まり: 「UPDATE と DELETE で値を書き換える設計は、既定では避ける」。採るのはクエリが書けないほど複雑・速さが致命的に落ちる・プロジェクトの決まり、のときだけ [skill-p3]
  - 3a 種類と無い値
    - 決まり: 迷ったらサブセットの表。区分の列だと種別で使わない列が NULL になる [skill-p3 ステップ1]
    - 判断28: 減量・増量の目標をサブセット weight_change_goals にし、期限と速さの案を移す。行の無い目標は維持（判断29）。向きは行の有無と体重の大小で出す（判断30）
    - 判断32: NULL を許す列は無い。判断33: どの表も書き足すだけ。今の目標と今の推定は引き方で出す
  - 3b 書き足す理由
    - 判定の5条件（過去の値を見る画面／監査／時機や理由の確認／ほかの状態に効く／将来履歴が要りそう）。どれにも当たらず書き換えるなら、将来の場面と互換を示してユーザーに委ねる [skill-p3 ステップ3]
    - (1) 過去の値を見る画面: ストーリー68「過去の日を見る人として、その日に当たっていた1日の目安と比べたい。あとで目標を立て直しても、その日の評価が変わらないため」。判断9: 過去の日の丸は、その日を含む目標の1日の目安のうち当てる始まりの日がその日以前で最も遅いものと比べる。表は daily_guides（goal_id, effective_on で一意）
    - 頻度: #613 の仕様では週の見直しで1日の目安が毎週変わりうる。目標の画面に推定消費カロリーと1日の目安の推移も出す [613]。ストーリー22「新しい目標の1日の目安が見直しで上書きされないため」はひと言
    - C の例え話との関係: nu-tori では最初から要件（条件1）。例え話は要件があとから来た場合（条件5）として書く
    - (2) 順番が入れ替わる事実: #647 設計判断1（D2）「サブスクリプションをリソース、取引をイベントにし、『今の状態』を1行に持って通知で書き換えない。順番が入れ替わった通知も、届いた取引を全部持てば同じ答えになる」。ストーリー58「古い通知で新しい状態を戻さないため」。根拠は素材の Apple の送り直しの決まり。「まれだが、起きたら上書きの表は古い状態に戻る」
  - 3c 消す理由
    - #332: 料理・食事を消すときは中身を消し、ID と控えだけを削除の印に残す。プライバシーポリシーの「消したものの ID を、消したことの印として残します」「どの食事の分だったかは残りません」に合わせる。代わりに「消した料理を『元に戻す』は、サーバーではできない」
    - 書き換えでなく足す側も #332 にある: 直した値は修正の行として足す。フェーズ3 の既定に従う（「あとから『元に戻す』を足せる形」）。残す・消すを同じ機能の中で理由で分けた例として出す
- 4 関係
  - 決まり: 1:N は N の側に外部キー。ただし互いに依存しないなら中間の表を置く。問いは「A が無くても B は在りうるか」「B がどの A にも結び付かない状態はありうるか」[skill-p4]
  - 判断39: 外部キーを子に直に置き、中間の表を足さない。［分析］問いに当てはめると、weight_change_goals・goal_closures・daily_guides はどれも目標なしに在りえない
  - 判断38: 目標どうしの関係は goal_closures が goals を2回指す（goal_id と next_goal_id UNIQUE）。SNS のフォローが同じ表を2回指すのと同じ形 [skill-p4 の例]
- 5 検証
