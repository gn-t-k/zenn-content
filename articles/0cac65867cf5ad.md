AI にコードを書いてもらうようになって、アプリのコードは気軽に直せるようになりました。多少まずい書き方をしても、あとで AI に頼めばすぐ直ります。細かいところまで気にしすぎなくていい、と感じている人も多いと思います。テーブルも AI に案を出してもらい、そのまま採ることが多いかもしれません。

ただ、テーブル設計は違います。コードはあとから直せても、保存し忘れたデータはどう頑張っても取り戻せません。たとえば、商品の価格を1つのカラムで上書きしていたとします。あとで「値下げした商品に、もとの価格を打ち消し線つきで並べる」機能を作ろうと思っても、もとの価格はもう残っていません。解釈の余地があるテーブルも困ります。NULL を許すカラムがあると、「このカラムが NULL とはどういう意味か」がテーブルの定義から読めず、AI を混乱させます。

この記事では、取り戻せない取り忘れも、解釈の余地も残さないためのテーブル設計の考え方を、ユースケースからテーブルができるまでの5つの工程に分けて紹介します。要になるのは、変わる値は上書きせずに書き足すのを既定にすることと、値が無いことをできるだけ行が無いことで表すことです。最近公開した個人開発アプリ「nu-tori」で、目標を立てる機能のテーブルを決めたときの例を交えて説明します。

https://nu-tori.app/

nu-tori は写真で食事を記録し、体重の傾向から、その日に摂るカロリーの目安を調整する iPhone アプリです。

## 5つの工程と、例にする目標の機能

nu-tori では、テーブルを次の5つの工程で設計しています。

1. **抽出**: 記録するもの（エンティティ）を、出来事から先に洗い出す
2. **正規化**: 1つの事実を1つの場所にだけ置く
3. **表現方法**: 種類の分け方、無いことがある値、変わる値の持ち方を決める
4. **関係**: 多重度を決め、外部キーと中間のテーブルを置く
5. **検証**: ユースケースごとに、読み書きを擬似 SQL で書けるか確かめる

各工程では、その工程の問いにだけ答えます。私はこの5つの工程を AI エージェントのスキルにして、AI と一緒にテーブルを設計しています。スキルでは、AI との進め方も決めています。

- 工程ごとに新しいサブエージェントに作業させる。先の工程の手順が目に入ると、今の工程を急ぐため
- 設計の状態と判断は、毎回ファイルに書く。会話の文脈が消えても、ファイルから再開できる
- 人に確かめるときは、選択肢とそれぞれの pros/cons を示す
- 今の工程の外の話は「パーキングロット」に書いておき、その工程で扱う

例にするのは、目標を立てる機能の仕様（[#523](https://github.com/gn-t-k/nu-tori/issues/523)）です。nu-tori の目標は、目標体重と向き（減量・維持・増量）を持ち、減量と増量には期限があります。目標を立てると、摂取カロリーの目安が出ます。目標は立て直すことができ、立て直すと前の目標は閉じます。

この仕様で足したテーブルは8つです。どれも書き足すだけで、UPDATE も DELETE もしません。NULL を許すカラムもありません。#523 には、そこに至る設計判断が53個並んでいます。以下では、その判断を工程の順に並べ直して紹介します。

## 出来事から先に洗い出す

最初の工程では、記録するものを洗い出します。「〜する」「〜日」と言える出来事（イベント系）から先に探し、「〜名」と言える物（リソース系）は、出来事の「誰が」「何を」「どこで」から見つけます。物から始めると、どの出来事にも使われないエンティティを作りやすいからです。

見落としやすい出来事を探す観点もあります。そのひとつが「あるときだけ値が入る属性」です。キャンセル日時はキャンセルという出来事に、既読日時は既読という出来事にします。

#523 では、目標を閉じること、目標を達成したこと、期限の日を確定したことを、目標とは別の出来事にしました（設計判断6）。目標を閉じた日は、目標を立て直したときにだけ生まれる値です。この観点に当てはめると、`goals` テーブルに NULL を許す `closed_on` カラムを置く形にはならず、閉じたことは `goal_closures` テーブルの行として書き足します。`closed_on` カラムにすると、目標を閉じるたびに目標の行を UPDATE することになります。

## 1つの事実は1か所に置く

2つめの工程は正規化です。1つの事実を1つの場所にだけ置き、ほかのカラムから計算で出せる値（導出項目）は、元のデータからいつでも正確に出し直せるなら持ちません。テーブルを分けるかどうかは、事実がいくつあるかで決めます。「JOIN が増えてクエリが複雑になる」は、分けない理由にしません。

#523 には、同じ事実を2か所に持たないための判断があります。

- 目標を決める要求の受け取りは、受け取った時刻を持たない。目標の `decided_at` と同じ事実だから（設計判断15）
- `goal_closures` は閉じた目標と次の目標だけを持ち、終わった日と閉じた時刻は、次の目標の `started_on` と `decided_at` から出す（設計判断16）

設計判断16の形なら、「前の目標が終わった日」と「次の目標を始めた日」が食い違うことは起きません。同じ日を2か所に持っていないからです。

## 値が無いことも、値が変わったことも、行で表す

3つめの工程では、値が無いことの表し方と、変わる値・消す値の持ち方を決めます。ここで決めることが、導入で挙げた2つの困りごと、解釈の余地と取り戻せない取り忘れに直接効きます。

決まりは1つです。UPDATE と DELETE で値を書き換える設計は、既定では避けます。UPDATE と DELETE は過去の値を失わせ、将来の拡張を狭めるからです。採るのは、クエリが書けないほど複雑になる、速さが致命的に落ちる、プロジェクトの決まりがそう定めている、のどれかのときだけです。

### 種類はサブセットのテーブルにし、値が無いことは行が無いことで表す

種類のあるものは、種類を表すカラムを1つ置く形（区分のカラム）か、種類ごとに子のテーブルを分ける形（サブセットのテーブル）で表します。区分のカラムにすると、種類によって使わないカラムが NULL になります。迷ったらサブセットのテーブルにします。

#523 の目標には、減量・維持・増量の向きがあり、期限があるのは減量と増量だけです。区分のカラムにすると、維持の目標では期限のカラムが NULL になります。そうなると、その NULL が「維持だから期限が無い」のか「期限をまだ決めていない」のかは、テーブルの定義からは読めません。#523 では、減量と増量の目標をサブセットのテーブル `weight_change_goals` にして、期限と速さの案をそちらに移しました（設計判断28）。`weight_change_goals` に行の無い目標が、維持の目標です。

```sql
CREATE TABLE goals (
  id TEXT PRIMARY KEY,
  started_on TEXT NOT NULL,
  starting_weight_trend_kg REAL NOT NULL,
  target_weight_kg REAL NOT NULL,
  decided_at INTEGER NOT NULL,
  time_zone TEXT NOT NULL
);

CREATE TABLE weight_change_goals (
  goal_id TEXT PRIMARY KEY REFERENCES goals (id),
  deadline_on TEXT NOT NULL,
  pace_plan TEXT NOT NULL
);

CREATE TABLE goal_closures (
  goal_id TEXT PRIMARY KEY REFERENCES goals (id),
  next_goal_id TEXT NOT NULL REFERENCES goals (id)
);
```

閉じていない目標も同じで、`goal_closures` に行が無いことで表します。こうして、#523 のテーブルには NULL を許すカラムが1つもありません（設計判断32）。今の目標は、カラムに持たずに引き方で出します（設計判断33）。

NULL を1つでも残せば、そこが解釈の余地になります。なので、どうしても理由がない限り、NULL を許すカラムにはしません。NULL を許したくなる日時のカラムは出来事のテーブルに、関連先が決まっていない外部キーは中間のテーブルに、一部の行にしか値が無い属性はサブセットのテーブルに分けます。

また、空文字や `-1` のような値を NULL の代わりに使うこと（センチネル値）はしません。「まだ入っていない」のか「ユーザーが空文字や -1 を入れた」のかを見分けられないからです。

### 上書きしてよいかを5つの問いで確かめる

既定は書き足すことなので、確かめるのは上書きしてよいかのほうです。変えることや消すことがある値について、次のどれかに当たれば、上書きせずに出来事のテーブルに書き足すことを考えます。

- 過去の値を見る画面・帳票・分析がある
- 監査やコンプライアンスで変更の履歴が求められる
- 変えた時機や理由を、あとから確かめたい
- 変えることが、ほかのエンティティの状態に効く
- 将来の要件で履歴が要りそう

どれにも当たらなくても、すぐに上書きと決めるわけではありません。UPDATE や DELETE で書き換えるなら、将来、出来事のテーブルが要る具体的な場面と、あとから移るときの互換を示して、人に決めてもらいます。導入で挙げた価格の例は、最後の「将来の要件で履歴が要りそう」に当たります。

nu-tori の摂取カロリーの目安は、最初の「過去の値を見る画面がある」に当たります。過去の日を見るときは、その日に当たっていた目安と比べます（設計判断9）。あとで目標を立て直しても、その日の評価が変わらないようにするためです。そのため `daily_guides` テーブルは、目標と当てる始まりの日（`effective_on`）ごとに行を書き足し、上書きしません。この場面は、たまにしか起きないわけではありません。次の仕様（[#613](https://github.com/gn-t-k/nu-tori/issues/613)）では、毎週の見直しで目安が変わりうるからです。上書きするテーブルだったら、見直しのたびに前の週の目安が消えます。

過去の値を残す理由は、画面のほかにもあります。nu-tori の課金の仕様（[#647](https://github.com/gn-t-k/nu-tori/issues/647)）では、App Store から届くサーバー通知を記録します。ここでは、サブスクリプションの「今の状態」を1行に持って通知のたびに書き換えることはせず、通知が運んだ取引を出来事として全部持ちます。#647 の設計判断には、次のように書いています。

> 順番が入れ替わった通知も、届いた取引を全部持てば同じ答えになる

Apple のドキュメントによると、App Store Server Notifications V2 では、サーバーが成功の応答を返さなかった通知を、前の試行から 1、12、24、48、72 時間後に送り直します（本番の環境だけ）。受け損ねた古い通知が、あとの通知より遅れて届くことがあるわけです。サーバーが受け損ねたときだけなので、まれにしか起きません。ただ、起きたときに上書きのテーブルだと、遅れて届いた古い通知が新しい状態を古い状態に戻してしまいます。

https://developer.apple.com/documentation/appstoreservernotifications/responding-to-app-store-server-notifications

### 消すときは、消す理由を決める

書き足すのが既定でも、nu-tori は何も消さないわけではありません。食事を直す仕様（[#332](https://github.com/gn-t-k/nu-tori/issues/332)）では、残すものと消すものを理由で分けています。

料理の時刻・名前・量を直したときは、作ったときの値を書き換えず、修正の行を書き足します。今の値は、受け取った順でいちばんあとの修正です。ここは書き足す既定に従っています。

一方で、料理や食事を消したときは、中身を物理削除し、ID だけを削除の印に残します。プライバシーポリシーの「消したものの ID を、消したことの印として残します」「どの食事の分だったかは残りません」に合わせるためです。その代わり、消した料理を「元に戻す」ことは、サーバーではできません。#332 には、このトレードオフも書いています。

書き足すか消すかは、「削除禁止」のような一律の決まりではなく、理由で選びます。

## 関係は、子が親なしに在りうるかで決める

4つめの工程では、エンティティどうしの多重度を決め、外部キーと中間のテーブルを置きます。1対多なら多の側に外部キーを置きますが、1対多でも中間のテーブルを置くかを検討します。両者が互いに依存しないなら、多の側に外部キーを直に置くと、関連が決まらないあいだ NULL になるからです。

依存を確かめる問いは、「A が無くても B は在りうるか」と「B がどの A にも結び付かない状態はありうるか」です。両方に「はい」なら、中間のテーブルを置きます。

https://zenn.dev/praha/articles/65afb28caacd0b

#523 では、外部キーを子に直に置き、中間のテーブルを足していません（設計判断39）。問いに当てはめると、`weight_change_goals`、`goal_closures`、`daily_guides` は、どれも目標なしには在りえません。

目標どうしの関係は、`goal_closures` が `goals` を2回指す形にしました（設計判断38）。`goal_id` が閉じた目標を、`next_goal_id` が次の目標を指し、`next_goal_id` には一意の索引を置きます。SNS のフォローで、中間のテーブルがユーザーのテーブルを2回指すのと同じ形です。

## 擬似 SQL で今の値を引けるか確かめる

最後の工程では、ユースケースを1つずつたどり、読む（SELECT）と書く（INSERT）を擬似 SQL で書けるか確かめます。目で見て「書けそう」と判断すると、JOIN の道の欠けや、カラムの漏れを見落とすからです。

書き足すだけのテーブルでは、今の値をカラムに持ちません。そのため、今の値を引けるかをここで確かめます。#523 の今の目標は「`goal_closures` に行の無い目標」です。

```sql
-- 今の目標
SELECT g.*
FROM goals g
LEFT JOIN goal_closures c ON c.goal_id = g.id
WHERE c.goal_id IS NULL;

-- ある日に当たっていた摂取カロリーの目安（:goal_id はその日を含む目標）
SELECT *
FROM daily_guides
WHERE goal_id = :goal_id
  AND effective_on <= :day
ORDER BY effective_on DESC
LIMIT 1;
```

向き（減量・維持・増量）もカラムに持たず、`weight_change_goals` の行の有無と、目標体重と開始の日の体重の大小から出します。

書き足す形には代償もあります。#332 では、選んだ案の cons として「今の値を読むたびに出来事を引いて並べる」と書いています。そのうえで、索引で引けるとして、この代償を受け入れています。この工程は、書き足す形の代償が許せるかを確かめる場でもあります。

## あとから直せないものに、手間をかける

AI のおかげで、コードはあとから直せるものになりました。一方で、保存しなかったデータは、あとからどう頑張っても取り戻せません。テーブルの定義から意味が読めなければ、AI を混乱させます。

だから、テーブル設計では、あとから直せないほうに手間をかけます。変わる値は書き足すのを既定にして、上書きと削除は理由があるときだけ選びます。値が無いことは、どうしても理由がない限り NULL にせず、行が無いことで表して、テーブルの定義だけで意味が読めるようにします。そのうえで、工程を分けて1つずつ判断し、最後に擬似 SQL で確かめます。AI にテーブルの案を出してもらうときも、どの工程の判断なのか、上書きや削除を選ぶ理由は何かを確かめれば、取り戻せない取り忘れも、解釈の余地も残さないテーブルに近づけます。
