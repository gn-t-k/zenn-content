個人開発のアプリを Cloudflare で動かすなら、D1 や Turso、DO（Durable Objects）の SQLite ストレージのような、SQLite をもとにした DB が安くて便利です。

ただ、D1 は DB 1つあたり 10GB までです。DO にも、1つ 10GB という同じ上限があります。ユーザーが増えても使い続けるには、安いからと置くだけでは済まず、何か工夫が必要そうです。

アカウントをまたぐ集計が必要ないのであれば、アカウントごとに SQLite を作る設計を検討できます。この記事では、D1・Turso・DO のそれぞれで DB をアカウントごとに分けるとどうなるかを比べます。そのうえで具体例として、最近公開した個人開発アプリ nu-tori で DO を選んで何をしたか、どんな代償があったかを紹介します。最後に、自分のアプリに当てはめられる表を置きます。

## D1・Turso・DO で、DB をアカウントごとに分ける

DB 1つの上限を越えるには、DB を分けます。アカウントの記録がアカウントの中で閉じているなら、アカウントごとに DB を1つ持たせるのが素直な分け方です。上限は「全員で 10GB」から「1人で 10GB」になります。1ユーザーに1DB は、それ自体が目的ではなく、上限を越えるための手段です。

3つの DB で、アカウントごとに分けると次のようになります。

| | D1 を並べる | Turso をアカウントごとに置く | DO をアカウントごとに置く |
| --- | --- | --- | --- |
| DB 1つの上限 | 10GB（引き上げられない） | <!-- TODO: 調査中 --> | 10GB |
| DB の数 | 1アカウント 100万個まで | 有料プランは無制限 | 無制限 |
| DB の数による料金 | 10万個を超えると1つ月 $0.10 | なし。使っていない DB は保存量だけ | なし。要求を受けていない DO は保存量だけ |
| Worker からどう選ぶか | バインディングは設定で固定（1スクリプト約5,000個） | DB ごとのホスト名に HTTP でつなぐ | `idFromName` で実行時に選ぶ |
| スキーマの変更を全 DB に配る | 自分で配る | 自分で配る（全 DB に配る機能は新規ユーザーには廃止） | 各 DO が起動時に自分で当てる |

D1 は、公式の文書もユーザーごとやテナントごとに DB を分ける使い方を想定しています。ただ、Worker から D1 を使うバインディングは設定ファイルに書いて固定するもので、1つのスクリプトに約5,000個までです。ユーザーが増えるたびに設定を足すわけにはいきません。管理用の REST API から読み書きする手もありますが、Cloudflare API 全体に5分で1,200回の制限があります。

Turso は、有料プランなら DB を無制限に作れ、東京（AWS `ap-northeast-1`）にも置けます。Worker から見るとネットワークの向こうにある DB で、Developer プランでは書き込みのコミットに最大 50 ミリ秒の待ちが足されます。

DO は、アカウント ID から DO を引けば、その中の SQLite がそのアカウントの DB になります。DO のコードはその SQLite と同じマシンで動くので、SQL を投げるたびにネットワークを往復することもありません。

設定にも API の制限にも縛られずに、実行時にアカウントの DB を選べるのは Turso と DO です。そのうちコードと DB が同じ場所にあるのは DO だけです。

## 具体例：nu-tori は DO でアカウントごとの DB を作った

nu-tori は食事の記録を貯めるアプリです。1人が1年に貯める量を 5MB と見積もると、全員を1つの DB に入れた場合、1,000人で約2年で 10GB に届きます。記録はアカウントの中で閉じていて、アカウントをまたいで読む機能もありません。そこで、アカウントごとに DO を1つ置き、その SQLite を DB にしました。

DO にしたことで、DB を引く・書く・時刻で動かす・消す、のそれぞれが1つの DO の中で完結しています。

### アカウント ID から、そのアカウントの DB を引く

```ts:get-account-durable-object.ts
export const getAccountDurableObject = (env: Pick<Env, "ACCOUNT">, accountId: string) =>
  env.ACCOUNT.get(env.ACCOUNT.idFromName(accountId), { locationHint: "apac-ne" });
```

同じ名前からは、いつも同じ DO が返ります。新しいアカウントの DO は、初めて引いたときにできます。

### 読む → 決める → 書くを、1つのトランザクションに収める

DO のコードは SQLite と同じマシンで動くので、SQL を同期の関数として呼べます。`transactionSync` は同期のコールバックを受け取り、コールバックが終わるまでほかの処理は割り込みません。途中で例外が出れば、まとめて取り消されます。なので、読んだ結果を見て書くかを決める処理を、1つのトランザクションに収められます。

```ts
// 例: 読む → 決める → 書く を1つのトランザクションにする
this.ctx.storage.transactionSync(() => {
  const row = this.ctx.storage.sql
    .exec("SELECT status FROM jobs WHERE id = ?", id)
    .one();
  if (row.status !== "pending") return;
  this.ctx.storage.sql.exec("UPDATE jobs SET status = 'running' WHERE id = ?", id);
});
```

D1 でトランザクションになるのは、`batch()` に文を先にまとめて渡す形だけです。読んだ結果を見て次の文を決めることはできません。

nu-tori では、記録の書き込みをまるごと `transactionSync` の中で行っています。

### 期日の仕事を、アカウントごとに1つのアラームにまとめる

DO には、指定した時刻に自分を起こすアラームがあります。1つの DO に張れるアラームは1つで、ハンドラが例外を投げると、Cloudflare が2秒からの指数バックオフで最大6回やり直します。

nu-tori では、アラームで動かす仕事を1つの並びにまとめています。課金状態の確認、AI による栄養の推定、AI の返事、写真の後片付けなどです。

```ts:account-alarm-jobs.ts（抜粋）
export const accountAlarmJobs = [
  { advance: /* 課金状態の確認を進める */, computeNextAt: /* 次に確認する時刻 */ },
  { advance: /* 推定を進める */, computeNextAt: computeNextEstimationJobAt },
  // ...
];
```

アラームが鳴ると仕事を並びの順に進め、それぞれの「次の時刻」のうちいちばん早いものに次のアラームを張ります。仕事が失敗したらハンドラから例外を投げ、やり直しは Cloudflare に任せています。6回のやり直しを使い切っても、アプリから次の要求が来れば、そのあとに同じ並びから次の時刻を出し直して張り直します。

キューやスケジューラを別に用意しなくても、アカウントごとの期日の仕事が回ります。

### 要求とアラームで、同じメモリを使う

同じアカウントへの要求とアラームは、同じ DO のインスタンスが処理します。nu-tori では、アラームの中で AI が書いている返事の文を、アプリからの要求がメモリから受け取って、そのまま流しています。途中経過を DB に書いて読み直す必要がありません。

ただし、メモリに置いたものは DO がメモリから外れると消えます。消えて困るものは SQLite に書いておきます。

### アカウントの削除は `deleteAll` で済ませる

アカウントを消すときは、その DO の `deleteAll()` を呼べば、SQLite の中身がまとめて消えます。表ごとに `DELETE` を書いて、消し忘れの表がないか確かめる必要はありません。

ただし、DO の SQLite には30日分の PITR（過去の時点に戻す機能）があります。`deleteAll()` のあと、その履歴がどう扱われるかは文書に書かれていないので、30日は残りうると考えています。

## DO を選んだ代償

代わりに受け入れたことは5つあります。選ぶかどうかを左右する大きさの順に並べます。

### 全員をまたぐ SQL が書けない

DB がアカウントごとに分かれているので、「全ユーザーの記録を集計する」SQL は書けません。nu-tori では、分析に使う出来事を PostHog に送り、集計はそちらで行っています。

アカウントをまたぐ集計がアプリの機能に必要なら、この設計は向きません。

### スキーマの移行の失敗が、遅れて表に出る

DB がアカウントの数だけあるので、スキーマの変更も全 DB に当てる必要があります。nu-tori では、DO のコンストラクタで、まだ当てていない移行を当てています。

```ts:apply-durable-object-migrations.ts（抜粋）
const appliedVersions = readAppliedVersions(storage.sql);
const pendingMigrations = migrations
  .filter((migration) => !appliedVersions.has(migration.version))
  .toSorted((a, b) => a.version - b.version);
for (const migration of pendingMigrations) {
  storage.transactionSync(() => {
    storage.sql.exec(migration.sql);
    storage.sql.exec("INSERT INTO durable_object_migrations (version) VALUES (?)", migration.version);
  });
}
```

この形では、移行の失敗はその DO に初めて触れたときにしか表に出ません。デプロイした時点では、全員の DB に当たったかは分かりません。

nu-tori では、失敗を起こしにくくする工夫をしています。

- 当てたかどうかを、版の最大値ではなく、当てた版の集合で判断する。並行して作った移行が、版の大きいほうから先に入ることがあるため
- 移行は足すだけにし、前の版のコードでも動く形にする
- 移行の SQL は手で書く。Drizzle Kit の DO 用の `migrate`（0.45.3）は、最後に当てたものより古い時刻の移行を黙って飛ばすため

### 本番の DO の中を外から覗けない

D1 ならダッシュボードや Wrangler から SQL を投げられますが、DO の SQLite は DO のコードからしか読めません。調べたいことがあるたびに、それを返すコードを書いてデプロイすることになります。

### Cloudflare に強く縛られる

DO は Cloudflare 独自の仕組みです。nu-tori では、ドメイン層を Cloudflare から切り離し、スキーマを素の SQLite にしています。逃げ道は、アカウントごとの SQLite を Turso の東京に移すことです。

### D1 にはない料金がかかる

DO では、要求の回数（月100万回まで込み、超えると100万回ごとに $0.15）と、動いている時間（月40万 GB 秒まで込み）にも料金がかかります。D1 は、行の読み書きと保存量だけです。

## 自分のアプリに当てはめる

前提として、全員分のデータが 10GB に届かないなら、DB を分ける必要はありません。届きそうなら、次の表で効く／効かないを付けてみてください。

| 項目 | 効くアプリ | 効かないアプリ |
| --- | --- | --- |
| 実行時にアカウントの DB を引ける | アカウント数が増え続ける | ― |
| 読む → 決める → 書くを1つのトランザクションに収められる | 読んだ結果で書くかを決める処理が多い | 単純な読み書きが中心 |
| 期日の仕事を1つのアラームにまとめられる | アカウントごとに時刻の決まった仕事がある | 時刻で動く仕事がない |
| 要求とアラームで同じメモリを使える | 裏で作っている途中のものをアプリに流したい | ― |
| 削除が `deleteAll` で済む | アカウント削除を確実に行いたい | ― |
| 全員をまたぐ SQL が書けない | ― | アカウントをまたぐ集計が機能に必要 |
| 移行の失敗が遅れて表に出る | ― | 移行を頻繁に、大きく変える |
| 中を外から覗けない | ― | 本番のデータを SQL でよく調べる |
| Cloudflare に強く縛られる | ― | 別の基盤へ移る見込みがある |
| D1 にはない料金がかかる | ― | 要求が非常に多い |

いちばん大事な目安は、アカウントをまたぐ集計が必要かどうかです。必要ないなら、アカウントごとに DO を置き、その SQLite を DB にする設計を検討できます。
