## 成果物
### 企画
- スタートポイント: Durable Object をチャットやカウンターの例で知っている程度の開発者。DB は「アプリに1つ」が当たり前で、記録を貯めるふつうのアプリも DB 1つで組んでいる
- 懸念される出来事: （空。深追いしない）
- R1: そもそも「1ユーザーに1DB」という発想が無い。なので、DO を DB にする案を比べる候補に入れられず、入れたとしても何を得て何を払うのかが分からない
- R2: 自分のアプリで「アカウントごとの DO を DB にするか」を自分で選べる。達成条件は、記事の利点と代償の一覧を自分のアプリに当てはめて、それぞれ効く／効かないを付けられること
- 読者がすでに試したこと: DO の公式の例（リアルタイムの協調やカウンター）を見た程度。DB として使う例や、ユーザーごとに DB を分ける設計には触れていない
- 記事に使う事実（確認済み）:
  - 選んだ理由（ADR-0012 と開発者の言葉に限る）: 1つの決め手ではなく、SQLite の良さ、アカウントごとに DB を分ける設計などを合わせた結果。ADR に書かれた理由のうち、10GB の上限、計算と DB が同じ場所、費用、削除が丸ごと消すことで済む、を使う。WHERE 句の書き忘れは使わない
  - D1 をユーザーごとに分けない理由（2026-11-19 に公式の文書で確認し直した）: D1 は今「ユーザーごとの小さな DB を並べる設計」を想定し、1アカウント 100万 DB（10万まで込み）。ただし Worker に結べる D1 は1スクリプトに約5,000個で設定で固定。REST API は主に管理用で、Cloudflare API 全体に5分1,200回の制限がある。DO は idFromName で実行時に選べる
  - Cloudflare の挙動（公式の文書で確認）: transactionSync は同期のコールバック、例外でロールバック。D1 でトランザクションになるのは batch()。アラームは1つの DO に1つ、少なくとも1回、2秒からの指数バックオフで最大6回。PITR は30日。deleteAll は SQLite なら原子的。deleteAll のあと PITR の履歴が残るかは文書に記述なし。DO も1つ 10GB
  - 使わない主張: 前のセッションで崩れた6つ（通し番号の順、あとに受け取ったほうを採る、量の上限、行数でクエリが重くなる、要求を1本ずつ処理、WHERE 句の書き忘れ）。週の見直しをアラームで書くという ADR の記述（#1076 で実際と違う）
