個人開発のアプリを Cloudflare で動かすなら、D1 や Turso、DO（Durable Objects）の SQLite ストレージのような、SQLite をもとにした DB が安くて便利です。

ただ、D1 は DB 1つあたり 10GB までです。DO にも、1つ 10GB という同じ上限があります。ユーザーが増えても使い続けるには、安いからと置くだけでは済まず、何か工夫が必要そうです。

アカウントをまたぐ集計が必要ないのであれば、アカウントごとに SQLite を作る設計を検討できます。この記事では、1ユーザーに1DB を DO で実現した話、D1 や Turso との比較、DO ならではの工夫を、最近公開した個人開発アプリ nu-tori を例に話していきます。

## 成果物
### 企画
- スタートポイント: Durable Object をチャットやカウンターの例で知っている程度の開発者。DB は「アプリに1つ」が当たり前で、記録を貯めるふつうのアプリも DB 1つで組んでいる
- 懸念される出来事: （空。深追いしない）
- R1: そもそも「1ユーザーに1DB」という発想が無い。なので、DO を DB にする案を比べる候補に入れられず、入れたとしても何を得て何を払うのかが分からない
- R2: 自分のアプリで「アカウントごとの DO を DB にするか」を自分で選べる。達成条件は、記事の利点と代償の一覧を自分のアプリに当てはめて、それぞれ効く／効かないを付けられること
- 読者がすでに試したこと: DO の公式の例（リアルタイムの協調やカウンター）を見た程度。DB として使う例や、ユーザーごとに DB を分ける設計には触れていない
- 記事に使う事実（確認済み）:
  - 選んだ理由（ADR-0012 と開発者の言葉に限る）: 1つの決め手ではなく、SQLite の良さ、アカウントごとに DB を分ける設計などを合わせた結果。ADR に書かれた理由のうち、10GB の上限、計算と DB が同じ場所、費用、削除が丸ごと消すことで済む、を使う。WHERE 句の書き忘れは使わない
  - D1 をユーザーごとに分けない理由（2026-11-19 に公式の文書で確認し直した）: D1 は今「ユーザーごとの小さな DB を並べる設計」を想定し、1アカウント 100万 DB（10万まで込み）。ただし Worker に結べる D1 は1スクリプトに約5,000個で設定で固定。REST API は主に管理用で、Cloudflare API 全体に5分1,200回の制限がある。DO は idFromName で実行時に選べる
  - Cloudflare の挙動（公式の文書で確認）: transactionSync は同期のコールバック、例外でロールバック。D1 でトランザクションになるのは batch()。アラームは1つの DO に1つ、少なくとも1回、2秒からの指数バックオフで最大6回。PITR は30日。deleteAll は SQLite なら原子的。deleteAll のあと PITR の履歴が残るかは文書に記述なし。DO も1つ 10GB
  - 使わない主張: 前のセッションで崩れた6つ（通し番号の順、あとに受け取ったほうを採る、量の上限、行数でクエリが重くなる、要求を1本ずつ処理、WHERE 句の書き忘れ）。週の見直しをアラームで書くという ADR の記述（#1076 で実際と違う）。「選んだ理由」と「使ってから得たもの」の書き分け（開発者が何を知っていたかは記事の価値に関係しないので、DO で何ができるかだけ書く）。laiso「個人開発のコストはDB次第」（2022）の引用（2026年は $5 前後で SQL DB が持てるので反論されやすい。費用は Cloudflare 公式の料金だけを根拠にする）。nu-tori の実際の月額（まだ分からない）

### 構造
- 主題: アカウントごとの Durable Object を、記録を置く DB にする設計
- 疑問: 安い SQLite 系の DB を使い続けたいが、DB 1つの容量の上限に届きそうなとき、アカウントごとの DO に分けると何が手に入り、何を払うのか。自分のアプリで選ぶべきか
- 主ポイント: SQLite 系は安いが、DB 1つに 10GB の上限がある。届きそうなら DB を分ける必要があり、アカウントをまたぐ集計が要らないなら、アカウントごとの DO に分けるのが素直で、上限以外の利点も付いてくる。代償もはっきりしているので、一覧を当てはめれば選べる
- キーライン:
  - 1. 安い SQLite には DB 1つの上限がある。届きそうなら分ける
    - SQLite 系（D1・DO・Turso）は、DB 1つあたりの固定費がなく、使っていない DB は保存量しか払わない（Cloudflare 公式の料金）。だから分けても費用が膨らまない
    - D1 は1つ 10GB。nu-tori の見積もりでは 1,000人で約2年で届く。開発者は「現実的に届きうる（届かせたい）」と考えた
    - 1ユーザー1DB は目的ではなく、上限を越える手段
  - 2. 分けるなら、D1 を並べる・Turso をアカウントごとに置く・DO を置く、の3つを比べて DO が素直（Turso の事実は公式の文書で確かめてから使う）
    - D1: 1アカウント 100万個（10万を超えると1つ月 $0.10）。Worker に結べるのは設定で固定の約5,000個。REST API は管理用で 5分1,200回の制限
    - DO: オブジェクト数は無制限、有料プランならアカウント全体の保存量も無制限。上限は DO 1つ 10GB だけ。idFromName(accountId) で実行時に選べる（get-account-durable-object.ts）
  - 3. DO ならではの利点（アカウントごとに分けると付いてくるもの）
    - 10GB が全員でではなく1人で10GBになる
    - 処理と DB が同じ場所にあり、読む→決める→書くが1つの同期トランザクションに収まる（transactionSync。D1 でトランザクションになるのは先に文を渡す batch() だけ）
    - 期日の仕事をアカウントごとに1つのアラームにまとめ、やり直しを Cloudflare に任せられる。要求とアラームで同じメモリ（返答の流れ）を使える
    - アカウント削除が deleteAll で済む（ただし PITR に30日残りうる）
  - 4. 払うものと、そのための工夫（それぞれ nu-tori の工夫を添える）
    - 移行は各 DO が起動時に当てるので、失敗はその DO に初めて触れたときに表に出る（版の集合で判断、追加のみ、前の版と両立）
    - 全員をまたぐ SQL が書けない（分析は PostHog へ）
    - 本番の DO の中を外から覗けない
    - ロックイン（逃げ道として Turso 東京を用意。Supabase による Turso 買収の報は未確認なので、触れるなら確かめてから）
    - D1 にない料金がある: DO への要求の回数（月100万回まで込み、超過 $0.15/100万）と動いている時間（月40万 GB 秒まで込み）。保存量は DO のほうが安い（$0.20/GB 月、D1 は $0.75）
  - 5. まとめ: 効く／効かないを付けられる表。目安は「10GB に届きそうか」「アカウントをまたぐ集計が要るか」
- 狙いワード（仮）:
  - 主: Durable Objects D1（DO と D1 のどちらを使うか比べたい人の語で、記事の問いに合う。トレンド（全世界・過去1年）で durable objects sqlite と同程度かやや上）
  - 補助: Durable Objects SQLite、D1 10GB
  - 想定読者: Cloudflare で D1 を使っている／検討していて、DB 1つ 10GB の上限や、DO の SQLite を DB にできるかが気になっている個人開発者
  - 根拠: サジェストに「d1 vs durable objects」「durable objects sqlite」「cloudflare d1 10gb」。「cloudflare d1 制限」はトレンドでほぼ0なので外した。「1ユーザー1db」系はサジェスト0件。日本語で DO をユーザーごとの DB にする記事は上位に見当たらない。どの語も検索数は小さく、2026年7月以降はほぼ0
