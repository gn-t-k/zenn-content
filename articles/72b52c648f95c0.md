同じチームの同僚が、この2ヶ月ほどでECサイトのフロントエンド（Next.js App Router）を集中的にリファクタしていました。横で見ていて「うまいなあ」と思う場面が多く、PRを読み返すほどに学びがあったので、特に唸った3つの手口を紹介します。

- 分岐プロパティを **Compound Component** にほどく
- **過剰な抽象を解体する**（Context・カスタムフック・汎用モジュール）
- フォームの手書き状態管理を **conform** に寄せる

それぞれについて「何をしたか（Before/After）」「何が良くなったか」に加えて、**「自分のコードベースで同じ問題をどう見つけるか」** も書きます。リファクタの記事はBefore/Afterを眺めて終わりになりがちですが、実際に価値があるのは「探し方」のほうだと思うからです。

なお、このリファクタは「FE直したい所」という雑な壁打ちissue（7項目の箇条書き）から始まり、50本以上の小さなPRに分割されて進みました。この進め方自体も良かったので、最後に少しだけ触れます。

# その1: 分岐プロパティをCompound Componentにほどく

## Before: `kind`プロパティで表示内容を振り分ける

エラー画面のコンポーネントが、こういう形をしていました。

```tsx
// Before（簡略化）
type Props = {
  kind: 'not-found' | 'payment-failed' | 'unknown';
};

export const ApplicationError: FC<Props> = ({ kind }) => {
  return (
    <div className={styles.wrapper}>
      <Image src="/assets/img/error.png" ... />
      {kind === 'not-found' && (
        <>
          <h1>ページが見つかりません</h1>
          <p>URLをお確かめください</p>
        </>
      )}
      {kind === 'payment-failed' && (
        // ...
      )}
      {/* kindが増えるたびにここが伸びる */}
    </div>
  );
};
```

よくある形です。最初は2分岐で済んでいたものが、エラーの種類が増えるたびにコンポーネント内部の分岐が育っていき、「ちょっと文言を変えたいだけ」の変更でもこのファイルを触ることになります。

## After: 枠と中身を分離して、呼び出し側で合成する

リファクタ後は、コンポーネントを「枠」と「部品」に分解しました。

```tsx
// After: application-error.tsx（簡略化）
export const ApplicationError: FC<ComponentProps<'div'>> = ({ children, ...props }) => {
  return (
    <div {...props} className={styles.wrapper}>
      <Image src="/assets/img/error.png" ... />
      {children}
      <Button asChild>
        <Link href="/mypage">マイページへ</Link>
      </Button>
    </div>
  );
};

// application-error-title.tsx / application-error-message.tsx も同様に小さな部品として定義
```

呼び出し側はこうなります。

```tsx
<ApplicationError>
  <ApplicationErrorTitle>ページが見つかりません</ApplicationErrorTitle>
  <ApplicationErrorMessage>URLをお確かめください</ApplicationErrorMessage>
</ApplicationError>
```

いわゆるCompound Component（合成コンポーネント）パターンです。エラーの種類が増えても`ApplicationError`本体は変更不要で、レイアウトや画像などの共通部分だけがコンポーネントの責務として残ります。

## 白眉: 文字数カウンター付きTextarea

このパターンの応用として一番感心したのが、Textareaの文字数カウンターです。

Beforeでは、呼び出し側が文字数の計算とフォーマットを自前で持っていました。

```tsx
// Before: 呼び出し側が表示ロジックを持っている
<div className={styles.textarea_wrapper}>
  <Textarea value={message} onChange={handleChange} maxLength={3000} />
  <div className={styles.character_count}>{message.length}/3000字</div>
</div>
```

Afterでは、カウンターが合成用の部品になりました。

```tsx
// After
<TextareaField>
  <TextareaFieldInput rows={3} maxLength={3000} value={message} onChange={handleChange} />
  <TextareaFieldCounter />
</TextareaField>
```

`TextareaField`がContext Providerになっていて、子の`TextareaFieldInput`から`value`と`maxLength`を拾い、`TextareaFieldCounter`がそれを表示します。呼び出し側は「カウンターを置くかどうか」「どこに置くか」だけを決めればよく、`length`の計算も`/3000字`のフォーマットも知らなくてよくなりました。

実装で面白いのは、**制御・非制御どちらのtextareaでも動く**ようになっているところです。

```tsx
// TextareaFieldCounter の内部（簡略化）
const context = useTextFieldContext();
const [length, setLength] = useState(0);

useLayoutEffect(() => {
  // 制御コンポーネントなら props.value の長さをそのまま使うので何もしない
  if (context.length !== undefined) return;

  // 非制御なら DOM の input イベントを購読して追従する
  const textarea = context.ref.current;
  if (!textarea) return;
  const update = () => setLength(textarea.value.length);
  update();
  textarea.addEventListener('input', update);
  return () => textarea.removeEventListener('input', update);
}, [context.ref, context.length]);
```

制御時は親の再レンダーに乗るだけ、非制御時だけDOMイベントにフォールバックする。部品を汎用化するときに「うちのユースケースだけ動けばいい」で止めず、コンポーネントとしての一般的な契約（制御/非制御）を守っているのが丁寧です。

ちなみにこのPRのレビューでは「invalid時に赤いoutlineが消えた」という指摘に対して、**「outlineはフォーカスリングの表示に用いるものであり、invalidだろうと色を変えるべきではない。invalid状態はborderで表現できている」** という返しがありました。フォーカス表現とバリデーション表現の責務分離。こういう設計原則がレビューの場で言語化されて残るのも、リファクタの副産物として価値がありました。

## 自分のコードベースでの見つけ方

- `kind` / `variant` / `type` のようなpropsを受け取って、内部でswitchや三項演算子で**表示内容そのもの**を振り分けているコンポーネントを探す。`grep -r "kind" --include="*.tsx"` してprops定義と分岐の組を目視するだけでも候補は出ます
  - 見た目のバリエーション（色・サイズ）の分岐は問題ないことが多い。**「中に置くJSXが分岐している」** のがサイン
- 呼び出し側に漏れた表示ロジックを探す。文字数カウント、日付フォーマット、単位の付与などを**コンポーネントの外側で毎回書いていないか**。同じJSXの並びが2箇所以上あれば合成コンポーネント候補

# その2: 過剰な抽象の解体

このリファクタ群でいちばん多かったのが、実は「何かを導入する」変更ではなく「**抽象を剥がす**」変更でした。3パターン紹介します。

## Context → ただのprops

クレジットカード入力フォームには、決済SDKの初期化失敗を親に伝えるためだけのContextがありました。

```tsx
// Before（簡略化）
const InitFailedContext = createContext<boolean | undefined>(undefined);

export const useCreditCardElementsInitFailed = () => {
  // Provider配下でboolean を取得。利用側は useEffect + ref で「一度だけ」通知に変換
};
```

伝えたいのは「初期化に失敗した」という**1回きりのイベント1つ**です。それをbooleanのContextで表現していたので、受け側には「stateの変化をイベントに読み替える」ためのuseEffectとrefが必要になっていました。

Afterはコールバックpropsです。

```tsx
// After（簡略化）
export const CheckoutCreditCardEditFormProvider: FC<Props> = ({ children, onInitFailed }) => {
  const onInitFailedEvent = useEffectEvent(onInitFailed ?? (() => {}));
  const client = useMemo(() => initPaymentSdk(), []);

  useEffect(() => {
    let mounted = true;
    client.catch((error) => {
      captureException(error);
      if (!mounted) return;
      addToast({ ... });
      onInitFailedEvent();
    });
    return () => { mounted = false; };
  }, [client]);

  return <Elements client={client}>{children}</Elements>;
};
```

Contextが正当化されるのは「深い階層の複数の子孫が同じ値を読む」ときで、親子間のイベント通知1本ならpropsで十分——書いてしまえば当たり前ですが、一度Contextで書かれたコードを「これpropsでよくない?」と言って剥がすのは、意外と誰もやりません。

## カスタムフック → ただの関数

カード情報のトークン化処理が、こういう構造になっていました。

```
useCreditCardTokenize()  ← hook。内部で useMultiPayment() / useElements() を呼ぶ
  └─ getTokenForElements()  ← third-parties/ 配下の「汎用」モジュール
```

Afterでは、hookを廃止して純粋関数にしました。

```tsx
// After: フォームコンポーネント側で依存を明示的に取得して……
const client = useMultiPayment();
const element = useElements()?.getElement('cardNumber');

// ただの関数に渡す
const result = await creditCardTokenizer(client, { element, cardholderName });
```

ポイントは、**このhookがhookである理由は「依存を内部で取得していること」だけだった**という点です。依存を引数に持ち上げてしまえば、残るのはただの非同期処理で、hooksのルール（呼び出し場所の制約、テストのしにくさ）に付き合う必要がなくなります。

## 「将来使うかもしれない」汎用モジュール → 利用箇所の配下へ

上記の`getTokenForElements`は`third-parties/`配下に「他のコンポーネントからも使える汎用モジュール」として置かれていましたが、PRにはこう書かれていました。

> `getSmbcTokenForElements`は他コンポーネントでは呼ばれていないため

実際には利用箇所が1つしかなかったので、汎用モジュール（＋そのテスト）を削除して、フォームコンポーネント配下の`internals/`に閉じ込めました。同様に、1ファイルからしかimportされていないスタイル定義をコンポーネントファイルに統合するだけのPRもありました。

「早すぎた汎用化を、利用実態に合わせて畳む」。機能は何も変わりませんが、コードを読む人が追いかけるファイル数と、「これ他でも使われてるかも」という気遣いのコストが確実に減ります。

## 自分のコードベースでの見つけ方

- **値を1つ配るだけ・通知1本だけのContext**: `grep -r "createContext"` して、Providerの`value`が単一のboolean/callbackのものを探す。「受け側にuseEffect+refでイベント化する処理がある」なら特に有力候補
- **外部状態に依存しないのにhookになっている処理**: `use`プレフィックスの関数のうち、内部でhooksを呼ぶ理由が「依存の取得」だけのもの。依存を引数で受ければ関数になれる
- **利用箇所が1つしかない「汎用」モジュール**: `shared/` `utils/` `lib/` 配下の各モジュールをimport元逆引き（`grep -rl "from '.*module-name'"`）して、参照数1のものをリストアップする。機械的に洗い出せるので、一度スクリプトを書いてしまうのがおすすめ

# その3: フォームの手書き状態管理をconformに寄せる

購入フロー（決済方法選択、カード情報入力、購入確定）のフォームが、それぞれ微妙に違う手書きの状態管理で実装されていました。これを [conform](https://conform.guide/) の新しいAPI（`@conform-to/react/future`）+ `useActionState` のパターンに統一していきました。

## Before: useTransition + preventDefault の手続き的なフォーム

```tsx
// Before（簡略化）
const [isPending, startTransition] = useTransition();
const [form, fields] = useForm({
  constraint: getValibotConstraint(schema),
  onValidate: ({ formData }) => parseWithValibot(formData, { schema }),
  onSubmit: (event, { submission }) => {
    event.preventDefault();
    if (submission?.status !== 'success') return;
    startTransition(async () => {
      // ここでトークン化 → API呼び出し → 画面遷移 を手続き的に書く
    });
  },
});
```

## After: useActionState + parseSubmission/report

```tsx
// After（簡略化）
const [state, action, isPending] = useActionState<SubmissionResult | null, FormData>(
  async (_state, payload) => {
    const submission = parseSubmission(payload);

    return await R.pipe(
      R.do(),
      // 1. スキーマ検証。失敗したら issues を report で返す
      R.bind('payload', () => R.pipe(
        R.parse(schema, submission.payload),
        R.mapError((issues) => report(submission, { error: { issues } })),
      )),
      // 2. カード情報のトークン化（その2で関数化したやつ）
      R.bind('token', ({ payload }) => R.pipe(
        creditCardTokenizer(client, { element, cardholderName: payload.cardholderName }),
        R.inspectError((error) => addToast({ ...error, variant: 'error' })),
        R.mapError(() => report(submission)),
      )),
      // 3. 送信して画面遷移
      R.andThen(({ payload, token }) => R.pipe(
        submit({ ... }),
        R.inspect((value) => router.push(value.redirectUrl)),
        R.map(() => report(submission)),
        R.mapError(() => report(submission)),
      )),
      R.orElse((error) => R.succeed(error)),
      R.unwrap(),
    );
  },
  null,
);

const { form, fields } = useForm(schema, { id, lastResult: state, defaultValue: { ... } });

return <form {...mergeProps(props, form.props)} action={action}>...</form>;
```

`R.pipe`は[byethrow](https://github.com/praha-inc/byethrow)というResult型ライブラリのパイプラインです。ここで効いているのは、conformの`report()`が**成功も失敗も`SubmissionResult`という単一の型に正規化してくれる**ことで、Resultパイプラインの各段の失敗（検証エラー、トークン化失敗、API失敗）がすべて「`report`して返す」に収束します。フォームの状態遷移が`useActionState`の1関数に閉じ、`preventDefault`も`startTransition`も手書きのpendingフラグも消えました。

このパターンを最初のフォーム（購入確定）で確立してから、カード編集フォーム、コンビニ決済選択、決済方法選択……と横展開していったのですが、その過程で面白い副産物が2つ生まれています。

## 副産物1: ダイアログをawaitする`toi()`

購入確定の途中には「クーポンを使わず購入しようとしていますが、いいですか?」という確認ダイアログが挟まります。従来は`DialogTrigger`方式（ダイアログをJSXツリーに常駐させて開閉stateを管理）でしたが、送信フローがアクション1関数に閉じたことで、「**フローの途中でダイアログを出して、ユーザーの選択をawaitしたい**」という形が素直になりました。

そこで作られたのが`toi()`（問い）というヘルパーです。

```tsx
// アクションの中で、ダイアログの結果を await できる
const confirmed = await toi<boolean>(({ resolve }) => (
  <Dialog onOpenChange={() => resolve(false)} defaultOpen>
    <CouponConfirmDialog onDiscard={() => resolve(false)} onConfirm={() => resolve(true)} />
  </Dialog>
));
if (!confirmed) return report(submission);
```

実装は`useSyncExternalStore`ベースの小さなストアに任意のコンポーネントを積んで、ルートに置いた`<ToiHost />`がそれをレンダリングし、`resolve`が呼ばれたら（閉じアニメーションの完了を待ってから）Promiseを解決する、というものです。全体で100行未満。

このヘルパーは後日、別の画面の「氏名に使えない文字が含まれています」エラー表示にもそのまま転用されました。従来この画面では、トーストに`duration: 'permanent'`を指定してリンクを埋め込むという苦しい実装でユーザーに2つの導線を提示していたのですが、`toi`＋ダイアログでボタン2つの明快なUIに置き換わっています。**リファクタで作った抽象が、次のUX改善のコストを下げた**わかりやすい例でした。

ちなみに`toi`の初版レビューでは「Escapeキーやオーバーレイクリックでダイアログを閉じると`resolve`が呼ばれず、Promiseが永久にpendingのままフォームが操作不能になる」というデッドロックが検出されて修正されています。ダイアログをPromise化するときの古典的な罠なので、真似する方はご注意を。

## 副産物2: 決済代行のiframeをconformの管理下に置く`useControl`

カード番号入力欄は決済代行サービスが提供するiframeで、DOM上は自分たちの`<input>`ではありません。従来は「入力完了したか」を独自のhookでuseState管理していました。

conform化にあたって、最初の実装では入力途中にもバリデーションエラーが即表示されてしまう回帰が出たのですが、レビューを経てconformの`useControl`を使う形に落ち着きました。

```tsx
const cardNumberControl = useControl<string>();

<CardNumberElement
  onChange={(event) => cardNumberControl.change(event.complete ? 'complete' : 'incomplete')}
/>
{/* iframe の状態を hidden input に写して、conform に「普通のフィールド」として扱わせる */}
<input
  id={fields.cardNumber.id}
  ref={(ref) => cardNumberControl.register(ref)}
  name={fields.cardNumber.name}
  hidden
/>
```

iframeの入力状態をhidden inputに写経することで、conformから見れば「値が`complete`かどうかをスキーマで検証するだけの普通のフィールド」になります。バリデーションのタイミング制御（送信時にまとめて検証）もconformのデフォルトに乗れて、独自hookは削除されました。**外部の制御不能な要素を、ライブラリの世界観の内側に翻訳して持ち込む**手筋として覚えておきたいやつです。

## 自分のコードベースでの見つけ方

- フォームごとに`useState`＋`useTransition`（または独自のisSubmitting）＋`event.preventDefault()`の組み合わせを手書きしていないか。フォームが2つ以上あって、それぞれ微妙に違う書き方をしていたら統一の好機
- 送信フローの途中に確認ダイアログが挟まるUIで、ダイアログの開閉stateとフォームの状態が絡み合っていないか（「confirm用のstate」「pending中フラグ」が並んでいたら候補）
- トーストに長時間表示やリンク埋め込みをしているエラー通知はないか。それは本来「ユーザーに選択を迫るダイアログ」かもしれません
- iframeやWeb Componentsなど、フォームライブラリが直接扱えない入力要素を独自stateで管理していないか。多くのフォームライブラリに`useControl`相当の統合APIがあります

# おわりに: 手口よりも効いていたかもしれない進め方

3つの手口を紹介しましたが、横で見ていて一番効いていたのは進め方かもしれません。

- **起点は雑な壁打ちissue**。「FE直したい所」というタイトルで、「featuresの中がapplication系しかなくて、これ意味あんの?状態」みたいな一人称の箇条書きが7項目。最初から精緻な設計ドキュメントを書こうとしていない
- **PRを徹底的に小さく割る**。カード編集フォームのリファクタ1つが、リネーム→ファイル移動→hook→関数化→conform移行→iframe統合の7本のPRに分割されていました。1本1本はレビューが数分で終わる粒度で、だからこそ前述のバグ検出がレビューで機能した
- **パターンを1箇所で確立してから横展開する**。最初のフォームで型を作り、そこで出た汎用課題（ダイアログのawait化）を基盤として切り出してから、残りのフォームに同じ型を適用していく

リファクタというと大掛かりな計画を立てたくなりますが、「雑に問題を書き出す→1箇所で型を作る→小さいPRで横展開する」の繰り返しで、2ヶ月後にコードベースの景色が変わっていました。まずは自分のコードベースで、この記事の「見つけ方」をいくつかgrepしてみてください。
